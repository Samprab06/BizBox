# Furniture proposals in selected and reference Matterport viewers

`buildInteriorProposal` (`lib/interior/proposal-state.ts`) maps immutable proposed catalog furniture to scan coordinates using an explicit model-bound rigid calibration. Inputs are meters, Y-up; `roomAnchor` is the draft point mapped to scan `origin`. Furniture keeps actual catalog dimensions and verified model offsets. The illustrative replay scale (0.5) is deliberately excluded. Reference placement remains illustrative rather than measured selected-unit geometry.

`attachFurnitureScene` (`components/interior/matterport-furniture.ts`) loads approved local catalog models with the Matterport SDK's native `mp.gltfLoader`, documented at https://developers.matterport.com/tutorials/models/. It does not import application Three.js constructors into Showcase. URLs are absolute same-origin catalog URLs so the nested iframe fetches the application assets. Model rotation is converted from radians to the loader's degree inputs; world placement is assigned to the SDK node position, while raw catalog X/Z centering and minimum-Y grounding offsets stay in loader-local coordinates. The pinned SDK rotates its loader pivot around its translated model child; passing world coordinates as loader-local position would rotate the entire world translation a second time. Models use unit scale. One SDK-native `mp.ambientLight` per nonempty proposal provides light for standard glTF materials; stopping its owning scene object releases it. This adds a light to the SDK scene graph rather than modifying captured scan photography.

Attach once per connected SDK and scope. `update(proposal)` replaces changed scenes and clears removed proposed objects. Equivalent visual updates are deduplicated. Aborted, failed and superseded creation retires new SDK objects; `dispose()` stops active objects and removes the abort listener. SDK native loader/object lifecycle owns model resources. The returned `loaded` status requires every SDK native loader to report `Loaded`. Loading state is polled at 100 ms with a 15-second deadline; `Error`, timeout, cancellation or superseded work rejects and retires replacement objects, preserving the prior successful scene. The pinned native loader cannot cancel its in-flight asset fetch and dereferences its pivot when that fetch returns; calling native stop while Loading causes a provider null-pivot error. Retirement therefore defers stop until native Loaded/Error. Caller waiting remains bounded at 15 seconds or immediate signal cancellation; a cleanup watcher remains until an uncancellable provider fetch reaches a terminal state. Updates are serialized, and superseded queued edits are skipped. `inspectModels()` exposes active native loader output roots for inspection without importing app Three constructors. Live browser verification is still required to establish correct visible placement.

The connected selected-space viewer observes `App.features` and `View.views`, then offers Original, Defurnished and Proposal. Defurnished requires an actual existing generated `ViewType.DEFURNISH` view and switches it with `View.setActive(false)`. A feature flag alone is insufficient. Missing views are explicitly unavailable; no generation endpoint or provider mutation is invoked. Original and Defurnished hide proposed furniture and simulated people; Proposal restores the shared draft/run overlays. Clearing proposals cannot erase furniture embedded in the photographed original. The explicit reference example remains separate from selected-building experiments.

Verification: `pnpm exec vitest run lib/interior/proposal-state.test.ts components/interior/matterport-furniture.test.ts` covers metric transforms/grounding, no replay shrinkage, clear behavior, native loader calls, scope rejection, cancellation, failure disposal and proposed Defurnish availability. No live provider mutation is used.

## Selected-building proposals

The generalized selected-site stage uses the resolved model identity rather than the café constant. `spatialScanCalibration` binds the draft to the selected model, floor, room and versioned SDK-coordinate bounds. A parent-building scan, missing dimensions, an unsupported envelope or a legacy coordinate cache remains viewable when approved, but receives no guessed metric overlay. The modeled proposal remains editable and runnable with its source assumptions shown.

`buildInteriorProposal().defurnish.available` is null: a pure layout transform cannot determine a live model's generated views. The connected viewer owns availability detection and switches an actual existing defurnished view using the documented SDK. This supersedes the earlier universally-unavailable flag; generating a new view still requires a separately established provider operation/access path.

The default workspace fetches the exact selected site interior with cancellation, validation and scope guards. A failed lookup retains an explicitly assumed modeled experiment and offers retry; it never substitutes Coffee Port. Suite-room bounds are approximate geometry, not verified doors, walls or service infrastructure. Entrance/service coordinate controls revise the same draft. `spatialScanReplay` projects its actual seeded run through the shared deterministic continuous-motion module; native scan, modeled SVG and 3D people use those positions and identities. Rendering stretches transit for readability without changing event times or report outcomes. Switching scan layers preserves the experiment state.

Live preparation is an explicit Run with Jev action; Run assumed preview is a separate local alternative. Neither scan loading nor scrubbing prepares decisions. Direct dragging of added furniture in the Matterport view is not implemented; catalog selection, move coordinates, rotation, removal and clear remain available in the experiment controls.

## Explicit authored scenarios

The generic stage can accept an explicitly supplied authored calibration. `selectedScanCalibration` requires an exact project, site, model and rectangle match, leaves `room.source` as `assumed`, and labels the transform `authored-preset`. This is an optional capability, not a default entry, generated room survey or fallback for another building. Entrance, service point, dimensions and existing obstacles remain scenario assumptions. Ordinary onboarding and selected-source discovery remain the main flow.

Source discovery distinguishes registry approval from the server's checked public viewing eligibility. A source-linked model can be eligible for public viewing without becoming a registry-approved mapping. The UI labels both facts separately; absent fresh status remains unverified, and SDK connection/rendering is reported independently by the viewer. Public viewing never promotes property geometry to selected-suite calibration. Unmapped scans keep furniture, moving people and reviewed experiment results on the explicitly modeled layout.

## Verified Defurnish API readiness (November 15, 2026)

A read-only query against the connected Model API confirms that both actual selected demo models expose bundle `mp:defurnish` ("Defurnished version of model"). For Gage `a5JGo8bjyeP` and Houston `S5rgSTufory`, its `availability` is `unavailable`, and `views(types:["matterport.model.defurnished"])` returns no views. This is a model/account capability result, not evidence that Matterport lacks Defurnish or an API representation.

The live mutation schema exposes `unlockModelBundle`; official add-on documentation describes bundle ordering and warns that some unlocks can charge the account. A successful Defurnish generation request through this mutation has not been established for an eligible model. Do not treat bundle presence alone as proof that generation can be triggered, or try to unlock an unavailable bundle. No mutation, order or generation was executed in this check.

Matterport's support guide documents generation through Cloud with model edit permissions and Defurnish enabled for the organization. Some models require reupload; copies of older models can remain ineligible despite a recent created date. The exact cause for these two models has not been determined. The guide describes a new AI-generated view that preserves the original model, removes non-fixed furniture as a whole, and can take hours. Commercial spaces may produce imperfect results.

Sources: [Defurnish your Space](https://support.matterport.com/s/article/Defurnish-your-Space?language=en_US), [Model API samples: existing defurnished views](https://developers.matterport.com/api/model/samples/), [bundle ordering](https://developers.matterport.com/api/model/ordering-addons/).

## Matterport-only FDE experiments

The selected-interior workspace uses the actual Matterport tour as its only canvas. It does not expose the separate modeled placement screen, catalog coordinate form, provider model IDs or attachment-path prose. Missing scans show a concise unavailable state. Technical source and scenario limitations remain in the report.

For “what happens if I add another table here?”, FDE uses `test_interior_change`. A trusted client action takes the current layout as its baseline, chooses a bounded valid placement near the current actual scan floor context, and adds exactly one catalog object. Upward floor intersections are checked against the current sweep floor elevation; a same-floor scan sweep ahead of the camera can provide a suggestion. If neither is available, the user points at a floor spot inside the tour. This is rigid meter placement, not verified suite reconstruction or proof that the entire proposed footprint avoids photographed furniture.

An assumed room can carry a `scan-floor-placement` alignment bound to its exact project, candidate, draft, model and room envelope. Native objects and the saved customer replay use the same transform. Late callbacks and pending placement requests cannot cross model/candidate/comparison boundaries. Native GLTF Loaded acknowledgment is required before the automatic paid-policy preparation begins; failure keeps the proposal unrun.

The experiment changes one object while preserving workload, paired seeds, hours, price, staff, service capacity, entrance/service anchors and existing proposed objects. A table adds no inferred seats or demand. Before/after ranges and paired differences are derived from the same completed run; zero and unfavorable outcomes are valid. A compact finding appears beside the tour. Keep result marks the current revision reviewed, and the final report preserves the question and recomputes the current finding. No separate toolbar or calibration workflow is required.
